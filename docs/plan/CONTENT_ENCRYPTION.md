## 1. 现状与问题

消息内容在服务器上全部是明文：

| 位置 | 内容 |
|---|---|
| `drops.title` / `body` / `extensions` | 标题、正文、扩展字段 |
| `attachments.safe_name` / `content_type` / `sha256` | 附件名、类型、明文哈希 |
| 存储后端（`FsStorage` 本地目录或 S3） | 附件原始字节 |
| `approvals.envelope` | 待审批发送的完整内容（标题、正文、扩展、附件 id、目标） |
| `approvals.reasons` | 审批原因，含 `附件名: 提示`（`attachments.ts:131` 生成，`send.ts:167` 写入，网页审批页原样显示） |
| `audit_events.meta.reasons`（`drop.send`） | 同上的附件名（`send.ts:193`） |
| `outbox_events.payload.title`（`drop.delivered`） | 标题（`send.ts:297`）；worker 从不删除这些行 |
| `drops.content_hash` / `approvals.content_hash` / `send_requests.request_hash` | 对内容的**无密钥** sha256，拿到库就能验证猜测的明文 |
| API 请求日志 | 搜索词：`GET …/drops?query=…` 的 URL 被原样记录（`app.ts` 的 `redactLoggedUrl` 只遮 `token=`） |
| 部署前自动备份和每日 `pg_dump` | 以上全部数据库内容 |

管理后台已经只给数量和大小。问题在于**任何拿到数据库、备份文件或附件目录的人都能直接读内容**。

## 2. 目标与威胁模型

**要防住的（离线或只读的暴露）：**

1. 数据库导出、部署前备份、每日备份及其异地副本被拷走或泄露。
2. 对数据库的**只读**访问：只读凭据泄露、只读 SQL 注入、从数据库主机偷走数据文件。
3. 只拿到附件存储（本地目录、S3 bucket 或其备份）。
4. 运维人员日常查库、排障时顺手看到内容。

**明确不防的**（与 Slack、Teams、飞书的默认配置相同，如实写明）：

1. **对数据库的写权限**。收件关系（`deliveries`、`delivery_grants`、`target_snapshot`）不受加密保护，能改库的人可以把别人的消息改成自己可见，再由运行中的 API 替他解密。数据库写权限等同于接管账号，需要靠数据库访问控制来保护，而不是靠内容加密。
2. 同时控制应用主机和密钥的人（root、能读密钥文件或进程内存）。
3. 被攻破的正在运行的 API/worker 进程。
4. 用户自己选择送出去的副本：飞书通知、浏览器推送、开发者 Webhook 里的标题，接收方 Agent 读到后写在本地的文件。
5. 元数据：谁、何时、给谁、多大，以及标题和正文的长度（AES-GCM 保留长度），仍然可见（§6.3）。

**必须保持的：**

- 每个人照常只能看到自己的消息；列表、阅读、导出、搜索、审批、附件、通知、助手回执的行为不变。
- 重置密码不影响已有消息（密钥由服务器管理，与用户密码无关）。
- 符合 ADR 0004：迁移只增不删，每一步都能回滚一步。
- CLI 和 MCP 的参数、返回字段不变。搜索的分页行为有变化，需要随之发一个 CLI 小版本，更新工具说明和 skill（§9）。

## 3. 业界做法（依据）

- **Slack**：默认加密存储；企业版 EKM 用信封加密，主密钥放在客户的 AWS KMS，数据密钥缓存在内存，每次解密都有 CloudTrail 日志，客户撤销密钥即可切断访问。EKM 不是端到端加密，不影响搜索和合规导出。
  （[Slack EKM](https://slack.com/help/articles/360019110974-Slack-Enterprise-Key-Management)，
  [工程实现](https://slack.engineering/engineering-dive-into-slack-enterprise-key-management/)）
- **Microsoft 365 / Teams**：服务端加密，Customer Key 让客户持有根密钥；明确说明它不阻止搜索和 eDiscovery；端到端加密只用于一对一通话和会议。查聊天内容需要单独的 eDiscovery 角色，全局管理员默认没有。
  （[Customer Key](https://learn.microsoft.com/en-us/purview/customer-key-overview)，
  [Teams 加密](https://learn.microsoft.com/en-us/microsoftteams/teams-encryption)，
  [eDiscovery 权限](https://learn.microsoft.com/en-us/purview/ediscovery-assign-permissions)）
- **Google Workspace**：静态加密；Vault 权限单独授予，搜索、导出进不可修改的审计日志；客户端加密开启后管理员只能看到主题和收发人。
  （[Vault](https://support.google.com/a/answer/2462365?hl=en)，
  [加密白皮书](https://services.google.com/fh/files/misc/google-workspace-encryption-wp.pdf)）
- **飞书**：默认加密落盘，「自主密钥」让企业替换默认密钥、可接第三方 KMS；2026 年起付费版需在 35 天内开启。
  （[自主密钥（基础版）](https://www.feishu.cn/hc/zh-CN/articles/244531857487-%E8%87%AA%E4%B8%BB%E5%AF%86%E9%92%A5-%E5%9F%BA%E7%A1%80%E7%89%88-%E4%BB%8B%E7%BB%8D)）
- **企业微信会话存档**：企业设定存档范围，外部联系人需本人同意；消息用企业公钥加密，只有企业私钥能解。
  （[接入指引](https://developer.work.weixin.qq.com/document/path/99871)）

结论：**服务端信封加密 + 密钥与数据分离 + 内容调取单独授权并留痕**，是企业协作产品的标准做法；端到端加密是少数场景的附加选项。本方案照此执行。

## 4. 设计总览

```text
主密钥 KEK（密钥文件，按 kid 分版本；不进数据库、不进备份、不进会被复制的 env 文件）
   └─ 包裹 ─▶ 数据密钥 DEK（每条 Drop / 每个附件 / 每个待审批各一把，随机 256 位）
                 └─ 加密 ─▶ 标题、正文、扩展字段、附件元数据、附件字节、待审批内容
```

- 算法：AES-256-GCM 和 HMAC-SHA256，都用 Node 内置的 `crypto`，不引入新依赖，两者都是 FIPS 认可算法。
- 加解密在应用层（domain 层）完成，数据库和存储后端只见到密文。
- 路由、MCP、CLI、网页看到的仍是明文，由 domain 层在返回前解密。
- **失败即关闭**：某行已经有 `dek`，就绝不回退去读明文列；库里一旦出现密文，没有密钥就拒绝启动。

## 5. 密钥体系

### 5.1 密钥环（keyring）

一个 JSON 文件，路径由 `CONTENT_KEYS_FILE` 指定：

```json
{
  "active": "k-3f9a1c2e",
  "keys": { "k-3f9a1c2e": "<base64 32 字节>" },
  "hmac": { "active": "h-8b41d07a", "keys": { "h-8b41d07a": "<base64 32 字节>" } }
}
```

- **kid 取密钥指纹**：`k-` 加上 `sha256("agentdrop/kid|" ‖ 密钥)` 的前 8 位十六进制，由生成脚本算出，不手写。这样各台服务器各自生成的 kid 天然不同，「重新生成了一个同名 k1」这种事故不会发生。启动时重新计算指纹，与文件里写的 kid 不一致就拒绝启动。
- **密钥校验行**：新表 `content_key_checks(kid, check_ct)`。每个 kid 首次使用时写入一段已知明文的密文；启动时逐个解一次，失败就拒绝启动。这可以挡住「文件被换成另一把同名密钥」「挂错了文件」。
- **加载规则**：
  - 只有 `NODE_ENV=test` 时才接受环境变量 `CONTENT_KEYS`。其他环境一律只读 `CONTENT_KEYS_FILE`。部署脚本常把环境配置和数据库备份放在一起：`deploy/pull-deploy.sh` 每次部署都会把所用的环境文件（`AGENTDROP_ENV_FILE`，默认 `.env.production`）复制进 `releases/<digest>/`，与部署前的数据库转储同目录；有的部署脚本还会把 `docker inspect` 的输出（含容器环境变量）随部署前备份一起保存。所以密钥不能出现在环境变量里。
  - 每把密钥解码后恰好 32 字节，`active` 必须存在。
  - 文件权限：`(mode & 0o077) == 0`，并且属主等于进程的 uid（容器里是 uid 1000）。
  - 日志只打印 kid。
- **什么时候必须有密钥**：库里存在任何 `content_key_checks` 行或 `dek` 非空的行，没有 keyring 就拒绝启动，就绪检查也失败。这个判断不依赖 `NODE_ENV`，因为不能假定每个部署都以 production 模式运行：`compose.local.yaml` 写死了 `NODE_ENV: development`，而 production 模式要求 S3 存储，用 fs 存储的部署本来就跑不了 production 模式。

### 5.2 DEK 的包裹格式

```text
wrapped_dek = 0x01 | len(kid) | kid | nonce(12) | AES-256-GCM(KEK, DEK) 密文(32) | tag(16)
AAD = "agentdrop/dek/v1|<kid>|<表名>|<行 id>"
```

- 用 GCM 而不是 AES-KW 包裹 DEK，是因为需要 AAD。每把 KEK 的包裹次数远低于随机 nonce 的安全上限（2^32），仍规定 KEK 每年轮换一次。
- AAD 把 DEK 绑到具体的行和 kid。行 id 一律取数据库里存的小写 UUID，不用请求参数里的原值。
- **行 id 由应用预先生成**（`randomUUID()`）。`drops`、`attachments`、`approvals` 现在由数据库 `defaultRandom()` 生成 id，写入后才拿到，而 AAD 需要先知道 id。数据库默认值保留，应用写入时显式传 id。
- 解包结果做进程内 LRU 缓存（约 5000 条、10 分钟）。**缓存键是 `H(wrapped_dek ‖ AAD)`**，保证命中缓存时 AAD 绑定依然成立。

### 5.3 字段密文格式

```text
field_ct = 0x01 | nonce(12) | AES-256-GCM(DEK, 明文 UTF-8) 密文 | tag(16)
AAD = "agentdrop/field/v1|<表名>|<行 id>|<字段名>"   （首字节的格式版本也计入 AAD）
```

每个字段独立随机 nonce；一把 DEK 只加密所在那一行的几个字段。AAD 含字段名，防止把 `body` 的密文换到 `title` 上。

同一行同一字段的旧密文被重放（把更新后的字段换回旧值），在这里不构成问题：Drop 创建后内容不可修改，待审批内容也只写一次。

### 5.4 将来接 KMS

`KeyProvider` 接口只有 `wrap`、`unwrap`、`activeKid`、`hmac`。第一版实现 `FileKeyProvider`；以后可接阿里云 KMS、AWS KMS、HashiCorp Vault Transit，主密钥不离开 KMS，每次解包都有 KMS 侧日志。本方案不实现 KMS。

## 6. 数据库字段加密

### 6.1 加密哪些

### 6.2 读写位置（完整清单）

写入：

- 附件分两步：
  - `stageAttachment`（`attachments.ts:38`，在收到字节**之前**写行）：生成 id 和 DEK，把 `{safe_name, content_type}` 加密写入 `meta_enc`。
  - `finalizeAttachment`（`attachments.ts:72`）：把 `sha256` 加进去，重新加密 `meta_enc`。

读取：

- 消息：`read.ts` 的 `summary()`（465）、`readDrop`（633）、`listGroupHistory`（285）；导出 `timeline.ts` 的 `readExportChunk`（259）。
- 审批：`approvals.ts` 的 `toView`（51）和 `decideApproval`（96、186）。
- 附件元数据：`toAttachmentMeta`（`read.ts:713`）的全部调用方，即 `read.ts:682`、`attachments.ts:105`（上传后返回的 `safe_name`）、`attachments.ts:160`、`timeline.ts:338`；另有 `attachmentsReviewHints`（`attachments.ts:128`，目前在 SQL 里直接读 `safe_name`）。

列表预览要解密整个正文再截 160 字。正文上限 64 KiB，一页 50 条最多解 3.2 MB，是毫秒级开销，不另存预览字段。

某一行解密失败时：该行在列表里显示为占位（「内容暂时无法读取」），同时记录 id 和 kid，其余行照常返回，不让整页报 `INTERNAL`。解出的 JSON 解析失败时，不记录 `err.message`，因为 V8 的报错信息会带上输入片段。

### 6.3 仍然明文的（接受的泄露）

id、时间、收发关系（`author_snapshot`、`target_snapshot`，路由、列表、导出筛选都要用）、`byte_size`（配额要用）、`body_chars`，以及由密文长度可推出的标题长度、附件数量、已读和收藏状态、`review_hints`。handle、昵称、群名属于账号资料，不在本方案范围。

## 7. 附件加密

### 7.1 分段流式加密格式

采用 STREAM 分段构造，与 Tink 流式 AEAD 的 nonce 布局相同：

```text
文件 = 头部 [magic "ADE1"(4) | 版本 0x01 | nonce 前缀(7)] + 若干段
每段明文 64 KiB，最后一段 0–64 KiB，各自 AES-256-GCM（authTagLength 固定 16）：
  nonce = 前缀(7) | 段序号(4, 大端) | 末段标志(1: 0x00 / 0x01)
  AAD   = "agentdrop/blob/v1|<attachment id>|" ‖ 头部全部字节
```

- 段序号防重排，末段标志防截断，头部计入 AAD 防止被替换或降级，attachment id 防止把一个附件的对象换成另一个。
- **边界规则**：
  - 加密时多读一段作为前瞻，以确定哪段是最后一段。
  - 0 字节文件写成一个空的末段。
  - 大小恰好是 64 KiB 整数倍时，最后一个整段就是末段。
  - 末段之后还有数据、段序号溢出、头部格式不对，一律拒绝。
- **解密不输出未认证的字节**：Node 的 GCM `update()` 会在认证之前就返回明文，所以每段先缓冲，`final()` 成功后才向下游输出；任何一段失败就销毁流、中断连接、记错误日志。
- 密文大小 = 12 + 明文大小 + 16 × 段数，段数至少为 1。

### 7.2 上传与下载

- 上传（`apps/api/src/routes/attachments.ts`），整条链路用 `stream.pipeline` 串起来，因为多级 `.pipe()` 不会传递错误（见文件 86–97 行的注释）：

  ```text
  请求流 → 64 KiB 探测（reviewHintsFromBytes，在明文上）→ 明文计量器 → 加密流 → storage.put
  ```

  - 明文计量器复用 `@agentdrop/storage` 的 `meter`，负责统计明文字节数和 sha256，超限时抛出 `StorageLimitError`（现有错误处理按这个类型判断）。
  - 传给 `storage.put` 的 `maxBytes` 按密文大小换算。
  - 第 105 行的 `Content-Length` 校验改用明文计量器的字节数。
  - `sha256` 和 `byte_size` 取自明文计量器；`storage.put` 返回的是密文的大小和哈希，只用来确认写入完整。
- 下载：`storage.get` → 解密流 → 响应。`Content-Length` 仍用明文 `byte_size`，`X-Agentdrop-Sha256` 从 `meta_enc` 解出，CLI 的下载校验（`cli/files.ts:111`）不变。
- 存储后端（`packages/storage`）不改，它只搬字节；`storage.test.ts` 不受影响。S3 的服务器端加密可以另外打开，作为额外保护。

| `outbox_events.payload.title` | worker 的 Webhook、飞书、推送**先在 R1 里**都改为用 `audience.title`，即按 `drop_id` 从库里读取并解密（`push.ts:112` 本来就读库）。开关打开后新事件不再带 `title`；回填时清掉旧行的 `title`。 |
| `approvals.reasons` 与 `audit_events.meta.reasons` 里的附件名 | 改存原因代码加 `attachment_id`（如 `{code:"secret_pattern", attachment_id}`）。网页审批页用 `t('…','…')` 做中英双语映射，需要时再解密附件名显示；审计记录里只存代码。回填时改写旧记录。 |
| 助手回执 | 读原 Drop 需要解密；生成的回执 Drop 走 `commitDrop`，自动加密。 |
| 导出 | 解密后输出，行为不变。 |
| 请求日志中的搜索词 | `redactLoggedUrl` 同时遮蔽 `query=`（这一改动 R1 就做，与加密无关，是现存问题）。 |
| 进程内存 | 生产容器关闭 core dump（`--ulimit core=0`，compose 用 `ulimits`），不在生产抓 heap snapshot；swap 的风险写进运维文档。 |

## 9. 搜索

现在 `list_drops` 的 `query` 和网页收件箱搜索，是在 SQL 里对 `title`、`body` 做 `ilike`（`read.ts` 136、202、298 行）。加密后无法再在 SQL 里匹配。

**服务端：应用层扫描，至少找到一条再返回。**

- 带 `query` 时，按原有顺序分批取候选行（每批 200），解密后做大小写不敏感的子串匹配。
- 停止条件：找到至少一条并已检查完当前批次，或者用完预算（2000 行或 1.5 秒）。
- `next_cursor` 指向**最后一条实际检查过的行**。
- 只扫当前查看者自己可见的行，所以结果条数和响应时间不会泄露别人的内容。
- 限流：搜索请求按用户限流（每分钟 30 次），同一用户最多并发 2 个。
- 游标格式 `{t,id,k}` 不变，`k` 已含查询串的哈希（`read.ts:46`）。
- 语义变化：现有的 `ilike` 没有转义 `%` 和 `_`，改为子串匹配后这两个字符按字面匹配（算是修正）；JS 的大小写折叠和 PostgreSQL 略有不同。都写进 CHANGELOG。

**网页端**（`apps/web/src/pages/mailbox.tsx`）：

- 现在只请求一页、没有翻页（97–110 行），有 `next_cursor` 时显示「仅显示最近 50 条」（303–306 行），结果为空时显示「没有消息」。
- 搜索状态下改为：结果为空但有 `next_cursor` 时，显示「在最近 N 条里没有找到」和「继续搜索」按钮；结果为空且没有 `next_cursor` 时，显示「没有匹配的消息」。文案中英双语。
- 搜索期间暂停 10 秒一次的自动刷新（`session.tsx:98`），避免反复扫描。

**MCP 与 CLI**：

- `renderList`（`packages/mcp/src/index.ts:347`）在结果为 0 条但有 `next_cursor` 时，输出「在已扫描范围内没有匹配，还有更早的消息：用 cursor 继续」。
- `list_drops` 的工具说明（`contracts/src/tools.ts:234`）和 skill 里补一句：「搜索结果少于 limit、甚至为 0 时，只要有 next_cursor 就还没搜完」。
- MCP 桥接和 skill 都打包在 CLI 里，所以需要**发一个 CLI 小版本**。老版本 CLI 仍然能用，只是可能过早停止翻页，属于体验问题，不会出错。

**否决**：盲索引会泄露词频，中文还要分词；确定性加密会泄露相同内容。等将来真有大邮箱，再考虑加密倒排索引。

## 10. 哈希与幂等

- **新的哈希定义**：`v2 = HMAC-SHA256(hmac_key, "agentdrop/content-hash/v2|" ‖ v1 的 sha256 十六进制)`，存成 `<hmac kid>:<十六进制>`，`hash_version=2`。v2 是在 v1 上再套一层 HMAC，所以**旧行不需要原文就能原地升级**。旧的 `send_requests.request_hash` 覆盖了目标和内容，回填时拿不到原始目标，没法按原文重算，用这个办法就能升级。
- **幂等比较**（`send.ts:116`）：先按新请求算出 v1，存储行是 v2 就再套 HMAC，然后比较。这样在 R1 与开关、R2 之间来回回滚，重试同一请求都不会误报 `IDEMPOTENCY_CONFLICT`。审批生成 Drop 时（`approvals.ts:186`），把哈希版本一并带过去。
- `hash_version` 在四张表上都定义为 `NOT NULL DEFAULT 1`，因为旧镜像插入时不会写这一列。
- **HMAC 密钥轮换**：新写入用新的 hmac kid；回填任务按行里记录的 kid 读出旧 HMAC，但由于 v1 值已不再保存，没法换钥重算。所以 `send_requests` 中超过幂等窗口（24 小时）的行直接删除；`drops` 和 `approvals` 的 `content_hash` 在需要时从解密后的内容重新计算。
- `attachments.sha256` 是给客户端做下载校验的明文文件哈希，客户端需要原值，所以移进 `meta_enc`，算法不变。

## 11. 代码结构

- **新目录 `packages/domain/src/content/`**。domain 包只在服务端使用，里面已经有 `crypto.ts`。不放进 `packages/security`：CLI 依赖并打包了 security 包（`apps/cli/package.json:20`），而 worker 反而不依赖它。
  - `keyring.ts`：`loadKeyring`、`FileKeyProvider`、指纹计算与校验、密钥校验行。
  - `cipher.ts`：`ContentCipher`，提供 `newDek`、`wrapDek`、`unwrapDek`（带缓存）、`seal`、`open`、`encryptStream`、`decryptStream`、`contentHmac`。
  - `codec.ts`：`sealDrop`、`openDrop`、`sealAttachmentMeta`、`openAttachmentMeta`、`sealApprovalPayload`、`openApprovalPayload`。所有读写只经过这几个函数，审查时一眼能看出还有没有漏掉的明文读写。
- **依赖传递**：domain 层现在不接收 storage，路由直接用 `ctx.storage`。`cipher` 改为作为参数显式传给 domain 函数。生产代码约 30 处调用点需要加这个参数，测试约 11 处。
  - `AppContext` 增加 `cipher`。
  - worker 目前把处理器写在 `main.ts` 的模块顶层，加载时就解析环境变量、连数据库，无法单测。先抽成 `createHandlers({db, cipher, fetch, log})`，再加加密。
- **配置**：
  - API 的 `config.ts` 和 worker 配置都新增 `CONTENT_KEYS_FILE`（仅测试环境接受 `CONTENT_KEYS`），以及 `CONTENT_ENCRYPTION=off|on`（§12）。
  - 测试工具（`harness.ts`）注入固定的测试 keyring；**现有全部测试在开关关闭和打开两种模式下各跑一遍**。
- **部署文件**：
  - compose 部署：新建 `compose.keys.yaml`，给 api、worker 挂载密钥文件并设置 `CONTENT_KEYS_FILE` 和 `ulimits`；`deploy/pull-deploy.sh` 在主机上存在密钥文件时自动把它加进 `COMPOSE` 列表。不改 `compose.local.yaml`，因为那份文件也用于本地试用，加上必需的挂载会让本地用户起不来。
  - 不用 compose 的平台：`CONTENT_KEYS_FILE` 要写进进程每次启动时实际读取的运行时配置（只在创建时读一次的初始化快照不算）；容器另加密钥文件的只读挂载，并关闭 core dump（`--ulimit core=0`，平台不支持时在入口脚本里关闭）。做法见 `docs/DEPLOY.md`。

## 12. 发布步骤与回滚

原先「三个版本」的写法违反了 ADR 0004：R3 一删列，R2 的镜像（Drizzle 按 schema 列出全部列）就会报「列不存在」；R2 回滚到 R1，Webhook 和飞书的标题会变空。修订后如下：

| 步骤 | 内容 | 回滚到上一步 |
|---|---|---|
| **R1**（服务端版本） | 迁移 `0021`：加新列、新表，放宽 NOT NULL，`hash_version` 默认 1。**完整实现读写加密，但由开关 `CONTENT_ENCRYPTION` 控制，默认 off**：off 时照旧写明文，但任何有 `dek` 的行都能解密读取，两种哈希都能校验；worker 通知统一从库里取标题；回填任务已注册，off 时不做任何事；遮蔽日志中的 `query=`。部署前在每台服务器上生成密钥并离线备份，R1 带着密钥上线，开关保持 off。 | 回到旧镜像：只加了列，旧镜像照常运行 |
| **开关打开**（改配置、重启，不换镜像） | `CONTENT_ENCRYPTION=on`：新写入全部加密，明文列写 NULL；outbox 不再带标题；审批原因存代码；哈希用 v2。回填任务开始运行（§13）。 | 把开关改回 off：R1 仍能读已写入的密文。**从这一步起不能再退回 R1 之前的旧镜像**（旧镜像读不了密文），这符合 ADR 0004「回滚一步」的规定 |
| **R2**（服务端版本，回填完成之后） | 加密变为强制，移除开关；回填完成后在 `content_state` 里关掉明文读取（`plaintext_reads=false`），此后即使明文列里有值也不读 | 回到 R1 并保持开关 on |
| **R3**（服务端版本） | 从 Drizzle schema 和代码里去掉明文列与回退逻辑，**数据库里的列仍保留** | 回到 R2：列还在，R2 可以正常读取 |
| **R4**（服务端版本） | 迁移删除明文列 | 回到 R3：R3 不引用这些列 |

说明：

- R1 就包含完整的加密实现，所以「R1 代码读加密后的数据」可以在同一份代码里用开关测出来，不需要保留旧分支。
- 各步骤之间至少间隔一个观察期（建议各一周）。
- 开关、R2、R3、R4 都只动服务端。只有搜索那一处需要一个 CLI 小版本（§9），可以和 R1 同时发。
- 两个版本之前的旧镜像跑在新数据上会出错（例如开关打开后，R1 之前的镜像遇到 `body` 为 NULL 会导致列表 500）。ADR 0004 只保证回滚一步，这在预期之内，这里写明。

## 13. 回填与物理清理

### 13.1 回填任务

回填**不放在单个 outbox 事件里一次跑完**：单个处理器有 300 秒超时、60 秒租约、最多重试 8 次（`main.ts:39–42`），附件多了会被打断，最后进死信。改为：

- `content.backfill` 事件每次只处理一小批：100 条 Drop 和审批，或者 5 个附件。处理完在同一事务里入队下一批，没有剩余就停止。整个过程幂等，中断后可以续跑，并且限速。
- Drop 和审批：同一事务里写入密文、明文列置 NULL、哈希升级为 v2。
- 附件：
  1. 读明文对象，加密写到新 key；
  2. 事务里更新 `storage_key`、`blob_format=1`、`dek`、`meta_enc`，旧 key 记入 `legacy_storage_key`；
  3. 提交后通过已有的 `attachment.cleanup` **延迟删除**旧对象，避开正在进行的下载。

  中途崩溃只会留下孤立的新对象，或者带有 `legacy_storage_key` 的行，都由后续批次继续清理。
- 旧的 outbox 行删除 `title`；`approvals.reasons` 和审计记录里的附件名改写为代码。
- `send_requests` 中超过 24 小时的行直接删除。
- 进度写日志；管理后台总览显示「内容加密：已开启（密钥 k-3f9a…）/ 回填剩余 N 条」。

### 13.2 物理清理（运维步骤，见 `docs/DEPLOY.md`；**删除备份不可逆，由运维者确认后执行**）

前提：回填完成，R2 已上线且关掉了明文读取，确定不会再退回开关 off 之前的状态。

1. **核对**：剩余明文为 0（总览数字，加一条校验 SQL）。做一次存储全量清点：每个对象都以 `ADE1` 开头并且有行引用它；没有引用的对象删除。
2. **数据库**：对 `drops`、`approvals`、`outbox_events`、`audit_events`、`send_requests` 执行 `VACUUM FULL`（会锁表，但数据量小，选低峰时段），它会重写数据文件、TOAST 和索引；再执行 `CHECKPOINT`。确认 `archive_mode` 关闭，没有保留旧 WAL 的归档。
3. **恢复演练（删除旧备份前必做）**：先做一份新备份（已无明文），用「新备份 + 离线保存的 keyring」在临时数据库上恢复，确认能读取消息，并抽查若干附件能下载、sha256 一致。
4. **删除含明文的旧备份**：
   - 部署脚本在每次部署前生成的数据库转储，例如 `deploy/pull-deploy.sh` 写在应用目录 `releases/<digest>/database-before.sql` 的那些，**其中包括部署 R1 时自动生成的一份**；
   - 其他部署脚本保存的部署前备份（数据库转储、随备份保存的 `docker inspect` 输出等）；
   - 每日 `pg_dump` 目录，以及 `DEPLOY.md` 里提到的所有异地副本。
5. **存储层残留**：S3 如开了版本控制，删除非当前版本；JuiceFS 清空回收站（`trash-days`）。本地文件系统和 JuiceFS 的删除都不是安全擦除，磁盘上可能仍有残留，这一点写明，不做承诺。

## 14. 密钥运维

**生成**（每台服务器各自生成、互不共用；在服务器上执行，密钥不经过任何聊天或提交）：

```bash
sudo install -d -m 0700 -o 1000 -g 1000 /etc/agentdrop
node packages/domain/dist/content/keygen.js > /tmp/k.json   # R1 新增的生成脚本，输出含指纹 kid 的 keyring
sudo install -m 0400 -o 1000 -g 1000 /tmp/k.json /etc/agentdrop/content-keys.json && shred -u /tmp/k.json
```

- 放在 `/etc/agentdrop/`，不放在应用目录（及其 `releases/`、备份目录）下，也不放进任何 `.env` 文件或平台的配置文件。
- 属主是容器里的 uid 1000，权限 0400。宿主机上随手建的 0600 文件，容器读不到，运维很可能改成 0644 去「修好」它，所以这里直接写明正确的属主和权限。
- 平台不允许宿主机绑定挂载、只能挂载卷时，把密钥放在卷上单独的目录里、应用目录和备份之外，只读挂载到 `/run/secrets/content-keys.json`；此时密钥和数据在同一个卷上，具体见 `docs/DEPLOY.md`。
- 注意：整机快照或整盘备份会把密钥和数据一起带走。这类快照要么排除 `/etc/agentdrop`，要么按「含密钥」的级别保管。

**离线备份（必须）**：密钥文件的离线副本放在密码管理器或离线介质里，并记下 kid。密钥丢失，所有内容连同所有备份都无法解密，没有任何恢复办法。部署 R1 前的检查清单第一项就是「密钥已离线备份，并且 kid 已核对」。

**定期轮换（每年一次）**：

1. 生成新密钥并加入文件，设为 `active`，重启服务；
2. 运行 `content.rewrap`，把全部 DEK 用新 KEK 重新包裹；
3. 旧 KEK 从在线文件中移除，离线副本保留到「所有用旧 KEK 包裹的备份都已过期删除」为止，然后销毁。

**泄露应对**：

| 泄露了什么 | 怎么处理 |
|---|---|
| **只泄露了 KEK**（密钥文件） | **只重新包裹是不够的**：所有旧备份里存的都是旧 KEK 包裹的 DEK，攻击者以后拿到任意一份旧备份仍能解密。必须：(1) 执行 `content.reencrypt`，为全部内容换新的 DEK 并用新 KEK 重新加密；(2) 销毁用旧 KEK 做的所有备份，或者把它们登记为已泄露；(3) 按事故流程通知。 |
| **泄露了 HMAC 密钥** | 轮换 HMAC 密钥；按 §10 重新计算 `content_hash`，删除旧的 `send_requests`。 |
| **密钥和数据同时泄露** | 内容视为已泄露，按事故流程处理，然后执行上面两项。 |

**恢复演练**：每次轮换后，以及每季度一次，按 §13.2 第 3 步做一遍。

## 15. 测试计划

**密码学单元测试**（`packages/domain/src/content/`）：

- 固定向量：给定密钥、nonce、明文，得到已知密文，防止格式被无意改动。
- 往返加解密。
- AAD 绑定：把 A 行的 `dek` 或 `title_enc` 拷到 B 行，解密失败；**命中缓存后也失败**。
- 篡改任意一个字节，解密失败。
- 流式加解密覆盖以下情况：
  - 0 字节、1 字节、恰好 64 KiB、64 KiB+1、多段；
  - 截断、重排段、删除末段、末段后追加数据、改动头部，都必须失败；
  - 某一段被篡改时，**这一段的字节一个都不输出**。
- keyring：密钥长度不对、缺少 `active`、kid 与指纹不符、文件权限过宽、属主不对、密钥校验行不匹配，都拒绝启动；轮换后旧数据仍可读。
- HMAC：v1 升级到 v2 的计算与幂等比较；按 kid 选择密钥。

**集成测试**（API 和 worker；**现有全部测试在开关 off 和 on 下各跑一遍**）：

- **库里没有明文**：发一条标题和正文都含特征串、带附件、会触发审批原因的消息，然后扫描 `drops`、`approvals`（包括 `reasons`）、`outbox_events`、`audit_events`、`send_requests` 的整行文本，以及存储目录下的全部文件字节，都不能出现特征串。
- **与加密前行为一致**：列表、阅读、分段阅读、群历史、导出、审批的预览与通过、助手回执、Web Push、飞书、Webhook 的输出。
- **附件**：上传 0 字节、1 字节、64 KiB 整数倍、64 KiB+1、20 MB 随机数据，下载的字节和 sha256 都完全一致；存储对象损坏时，下载中断且不输出错误数据；超限时仍返回原来的错误。
- **搜索**：
  - 匹配项排在第 3000 条之后时，按游标能翻到；
  - 结果为空但有 `next_cursor` 时，网页显示「继续搜索」，MCP 的文字提示也正确；
  - 搜索词不出现在请求日志里。
- **开关与回滚**：
  - off 写入 → on 读取；on 写入 → off 读取；
  - 回填中途杀掉进程再跑，结果一致；
  - 两种模式下，同一请求重试都不报幂等冲突；
  - 库里有密文但没有 keyring 时，拒绝启动，就绪检查也失败；
  - 某一行解密失败时，列表其余行照常返回。
- **worker**：抽出 `createHandlers` 后，开关打开时 Webhook、飞书、推送的标题取自数据库，不依赖 outbox 里的 payload。

**性能**：列表 50 条、搜索扫描 2000 条、100 MB 附件上传和下载，记录加密前后的耗时，写进 PR 说明。

## 17. 第二部分：合规调取（仅设计）

**适用场景**：把 AgentDrop 部署给公司或团队，组织在调查或法律要求下需要查看成员的消息。个人和朋友之间试用的服务器不需要这个功能。

**原则**（参照 Microsoft eDiscovery、Google Vault、企业微信会话存档）：

1. **与管理员分离**：新增独立能力「内容审查」。只有服务器配置 `CONTENT_AUDIT=on` 时这项功能才存在，默认关闭。普通管理员没有这项能力，也不能授予自己。
2. **授予和批准互相制约**：
   - 授予审查角色需要两位管理员中的另一位操作。
   - 每个案件有三方：申请人、批准人、被查对象，三者必须是不同的人。
   - 管理员不足两人时，这项功能不可用。
3. **按案件调取**：案件要写明事由，限定对象账号和时间范围，有效期最长 7 天。
   - 群消息只能查被查对象发出的消息，以及他作为收件人时看得到的消息；同群其他成员的内容，范围要在案件里明确列出。
4. **只读并留痕**：只能只读查看和导出；每次打开、导出都写审计日志，精确到 Drop id。
   - 审计日志要能发现篡改：用哈希链把记录串起来，并定期导出到数据库以外的地方。否则能改库的人照样能改日志。
5. **透明**：服务器开启内容审查时，所有用户都能在「设置」和「使用说明」里看到「本服务器的管理方可以在审批后调取消息」。是否逐案通知被查的人，由配置 `CONTENT_AUDIT_NOTIFY_SUBJECT` 决定。
6. **如实说明边界**：服务器运维者（能拿到主机和密钥的人）可以绕过这套流程。这套控制约束的是应用内的角色，约束不了运维者。

实施前需要决定：是否需要这个功能；是否逐案通知被查的人；授予和批准是否一律强制双人。

## 18. 否决的方案

| 方案 | 否决原因 |
|---|---|
| 现在就做端到端加密 | 搜索、导出、助手回执、飞书和推送的标题、合规调取、重置密码后恢复消息，要么做不了，要么要大改；Agent 之间如何分发密钥也是新问题。以后可以作为特定会话的选项。 |
| 只开磁盘或数据库透明加密 | 挡不住 `pg_dump`、备份文件和能连数据库的人。可以作为补充，不能替代。 |
| 用 PostgreSQL `pgcrypto` 在 SQL 里加解密 | 密钥会出现在 SQL 语句、日志和 `pg_stat_statements` 里，能连库的人就能解密。 |
| 用用户密码派生每个人的密钥 | 重置密码会丢失全部消息；群消息要为每个成员分别加密；Agent 凭证拿不到用户密码。 |
| 每个账号一把密钥 | 一条群消息对应多个收件人，要么存多份密文，要么共用密钥等于没分开。每条 Drop 一把密钥更自然，也方便以后按条销毁。 |
| 把加密代码放进 `packages/security` | 这个包会被打进 CLI，而 worker 反而不依赖它。 |
| 在一个 outbox 事件里跑完整个回填 | 会超过超时时间和重试上限，最后进死信。 |

## 19. 风险、未决问题与工作量

**风险：**

1. **密钥丢失等于全部数据丢失**（包括所有备份）。靠离线备份、kid 核对、密钥校验行和定期恢复演练来控制。
2. **密钥和数据在同一台主机上**，挡不住拿到主机 root 的人。要进一步分离，需要接入 KMS（§5.4），属于后续工作。
3. **数据库写权限不在保护范围内**（§2）。需要靠数据库账号权限、网络隔离、`pg_hba` 来防。
4. **物理残留**：PostgreSQL 的旧行版本、WAL、旧备份、文件系统里没有擦除的数据块。清理步骤见 §13.2，文件系统层面不做承诺。
5. **搜索性能**：邮箱很大时，应用层扫描会变慢；到时再做加密索引。
6. **运维复杂度**：多了一个必须妥善保管的文件，部署脚本、挂载、权限都要改，不同部署方式的差异写在 `docs/DEPLOY.md`。
7. **开发者 Webhook 仍然发送标题**：这是现有行为，`USER_GUIDE` 说的「不含正文」是准确的。要不要连标题也不发，另行决定。

**已决定（2026-09-25）：**

- (a) 搜索保留「继续搜索」，每次最多检查 2000 条（§9）。
- (b) 暂不接入 KMS，主密钥用服务器上的密钥文件（§5）。
- (c) §13.2 删除旧备份不可逆，由运维者在执行前单独确认。
- (d) 第二部分（合规调取）暂不做。

**R1 已完成：**迁移 `0021`；加密模块（密钥环、信封加密、流式加密、固定向量）；所有内容读写都经过编解码函数；应用层搜索和网页「继续搜索」；worker 从数据库取标题；启动时的失败即关闭；分批回填；管理后台显示加密状态；帮助页和用户指南按服务器状态显示；`compose.keys.yaml`，`deploy/pull-deploy.sh` 在有密钥文件时自动挂载；运维文档（`docs/DEPLOY.md`）。所有测试在开关关闭和打开两种模式下各跑一遍，另有专门测试确认库里和存储里没有明文、超出 2000 条仍能继续搜、开关可以双向切换、回填后一切可读。

**实现评审（2026-09-25）**：对全部代码改动做了一轮独立评审，没有阻断级问题，发现的问题都已修复并补了测试：

- 回填与上传中的附件存在竞态，可能导致对象永久以明文留存 → 回填跳过上传中的附件并等待；切换时加行锁复核状态和存储键；完成上传时加行锁；「已有密钥但对象仍是明文」的附件也会被处理。
- 开关「开 → 关 → 开」后回填不再运行 → 是否需要回填改为按数据判断，不再看已完成标记。
- 开关打开前创建、打开后才批准的审批，生成的消息带着无密钥的旧哈希 → 写入时就升级为有密钥的哈希；回填也会补升级。
- 一个坏附件会卡住整个回填 → 跳过并记录（`content_state.backfill.skipped`，仍计入剩余明文）；重新加密时核对明文 sha256。
- 旧对象的删除没有延迟 → outbox 支持延迟执行，旧对象 10 分钟后才删除。
- `compose.keys.yaml` 里的开关会覆盖 `env_file` → 开关改在各自的配置里设置。
- 游标只精确到毫秒，同一毫秒的行会被跳过（搜索时更明显）→ 游标改为 PostgreSQL 的微秒精度文本。
- HMAC 密钥也写入校验行；数据库用过、但密钥文件里已经没有的密钥，会在启动时报告出来。

**迁移演练（建议）**：在已有数据的服务器上开启之前，先用该服务器数据库和附件目录的副本建一个隔离的演练环境（单独的库、附件目录、只监听本机、专用密钥），走一遍迁移、回滚、比对、回填、明文检查和开关往返，确认无误后再动正式服务。演练结果属于运维记录，不进仓库。
